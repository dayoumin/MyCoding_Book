Agent review

Agent 설계와 운영 기준

agent를 먼저 역할 이름으로 만들지 않습니다. 작업 경계, 필요한 권한, 필요한 컨텍스트, 검증 방법이 분리될 때 agent로 나눕니다.

이번 검토의 결론

기본값은 단일 Codex, 분리 기준은 컨텍스트와 책임입니다.

작은 수정은 main agent가 직접 처리합니다. 조사량이 크거나, 구현 범위가 분리되거나, 리뷰 관점이 독립적일 때만 subagent 또는 custom agent를 씁니다.

agent를 나누는 기준

상황 권장 방식 이유
빠른 단일 파일 수정 Main Codex 컨텍스트 공유가 더 중요하고 agent 시작 비용이 아깝습니다.
코드베이스 여러 영역 조사 Explorer subagents 결과가 서로 독립적이면 병렬 탐색이 유리합니다.
파일 소유권이 분리된 구현 Worker agents 각 agent가 충돌 없는 범위를 맡을 때 속도가 납니다.
보안, 회귀, 테스트 위험 검토 Reviewer agent 구현자와 다른 관점으로 독립 검토합니다.
반복되는 절차 Skill agent보다 재사용 가능한 절차로 남기는 편이 좋습니다.
도구 실행 전후 정책 검사 Hook 또는 검증 명령 권한, 보안, 품질 기준을 자동 점검합니다.

Codex 기준 역할 세트

Main Coordinator

요구사항을 좁히고, 변경 범위를 정하고, 결과를 통합합니다. 사용자의 제품 의도를 계속 들고 갑니다.

Read Explorer

특정 질문에 답하기 위해 코드와 문서를 탐색합니다. 구현하지 않고 근거와 파일 위치를 돌려줍니다.

Write Worker

분리된 파일 범위에서 구현합니다. 다른 agent나 사용자의 변경을 되돌리지 않는 것이 핵심입니다.

Check Reviewer

보안, 회귀, 테스트 누락, UX 위험을 검토합니다. 결과는 발견 사항 중심으로 짧게 보고합니다.

메모리와 DB 선택

agentic coding이라고 해서 곧바로 vector store가 필요한 것은 아닙니다. 먼저 파일 검색, git 이력, 공식 문서 링크, 프로젝트 규칙으로 충분한지 확인합니다. 반복적으로 같은 도메인 지식을 찾아야 하거나, 문서가 많고 질문이 넓어질 때 RAG나 vector DB를 검토합니다.

  1. 1단계: repo search, git diff, AGENTS.md, README
  2. 2단계: 정리된 HTML/MD 학습 노트와 reference index
  3. 3단계: 문서 묶음 검색을 위한 file search 또는 vector store
  4. 4단계: 상태와 관계가 중요한 경우 structured DB 또는 graph
  5. 5단계: agent가 검색, 검증, 재시도를 고르는 agentic RAG
