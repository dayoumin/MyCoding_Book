MCP, Plugins, Connectors

외부 도구 연결은 agentic coding의 힘을 크게 올리지만, 권한과 검증 비용도 같이 커집니다. 이 문서는 Codex 기준으로 MCP, plugin, connector, app tool을 구분하고 언제 무엇을 쓸지 판단하는 기준입니다.

이번 결론

먼저 읽기 전용 연결부터 시작하고, 쓰기 권한은 검증 루프가 있을 때만 엽니다.

MCP는 모델에게 외부 도구와 context를 연결하는 표준 통로입니다. Codex에서는 CLI와 IDE extension이 MCP 설정을 공유하고, project-local 설정은 trusted project에서만 다룹니다.

Codex MCP 설정 기준

  • Codex MCP 설정은 다른 Codex 설정과 함께 config.toml에 둡니다.
  • 기본 전역 위치는 ~/.codex/config.toml입니다.
  • 프로젝트 범위 설정은 trusted project에서 .codex/config.toml로 둘 수 있습니다.
  • Codex CLI와 IDE extension은 같은 MCP 설정을 공유합니다.
  • 설정은 codex mcp CLI로 관리하거나 config.toml을 직접 편집할 수 있습니다.
  • Codex TUI에서는 /mcp로 활성 MCP 서버를 확인합니다.

Transport와 인증

방식 언제 쓰나 주의
STDIO 로컬 프로세스로 MCP 서버를 시작할 때 command, args, cwd, 환경 변수 전달 범위를 명확히 합니다.
Streamable HTTP 주소가 있는 원격 또는 로컬 HTTP MCP 서버에 연결할 때 bearer token, static header, env-based header 관리가 필요합니다.
OAuth 서버가 OAuth를 지원하고 계정 권한이 필요한 경우 codex mcp login <server-name> 흐름과 callback URL/port를 확인합니다.
Plugin-provided MCP 설치한 plugin이 MCP 서버를 함께 제공할 때 transport command는 plugin manifest 쪽에 있고, 사용자 설정은 on/off와 tool policy에 집중합니다.

최소 설정 예시

공개 문서에는 실제 개인 token이나 내부 URL을 넣지 않습니다. 아래는 구조를 보여주는 예시입니다.

[mcp_servers.docs]
command = "npx"
args = ["-y", "example-docs-mcp"]
env_vars = ["DOCS_READ_TOKEN"]

[mcp_servers.design]
url = "https://mcp.example.com/mcp"
bearer_token_env_var = "DESIGN_MCP_TOKEN"
enabled_tools = ["read_file", "search"]
default_tools_approval_mode = "prompt"

[mcp_servers.design.tools.read_file]
approval_mode = "approve"

권한 모델

  1. 서버 단위: 먼저 서버를 켤지 끌지 결정합니다. 임시 보류는 삭제보다 enabled = false가 낫습니다.
  2. 도구 목록: enabled_tools로 allowlist를 만들고, 위험한 도구는 disabled_tools로 다시 막습니다.
  3. 승인 모드: 기본은 prompt로 시작하고, 충분히 안전한 읽기 도구만 approve로 올립니다.
  4. 도구별 override: 같은 서버 안에서도 읽기, 쓰기, 삭제, 배포 도구의 승인 모드를 다르게 둡니다.
  5. timeout: 느린 서버는 startup_timeout_sec, tool_timeout_sec를 명시해 실패 모드를 예측 가능하게 만듭니다.

도입 전 질문

  • 이 연결이 단순 파일 검색이나 shell 명령보다 나은 이유가 있는가?
  • 읽기 전용으로 충분한가, 쓰기 권한이 꼭 필요한가?
  • 도구 결과를 어떤 테스트, diff, 화면, API 응답으로 검증할 것인가?
  • 실패했을 때 수동 복구가 가능한가?
  • 개인 계정, 고객 데이터, 내부 URL이 공개 문서나 로그에 섞이지 않는가?
  • 서버가 느리거나 죽었을 때 agent가 멈춰야 하는가, fallback을 써야 하는가?

운영 원칙

  1. 새 MCP는 읽기 전용, prompt 승인, 좁은 tool allowlist로 시작합니다.
  2. 쓰기 도구는 자동화하지 말고 diff, 로그, 배포 결과를 확인할 수 있을 때만 엽니다.
  3. 개인 playbook의 실제 서버명, token 이름, 내부 URL은 공개 HTML에 넣지 않습니다.
  4. plugin이 제공하는 MCP도 “plugin이 설치됐으니 안전하다”고 보지 말고 tool policy를 별도로 확인합니다.
  5. 외부 서비스 결과는 agent 답변만 믿지 않고 공식 링크, API 응답, 화면 캡처, 테스트로 검증합니다.
