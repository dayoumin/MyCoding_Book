Retrieval

Agentic RAG 운영 기준

Agentic coding에서 RAG는 “무조건 vector DB를 붙이는 것”이 아닙니다. agent가 필요한 지식을 찾고, 근거를 남기고, 부족하면 다시 검색하며, 결과를 검증하는 루프를 설계하는 일입니다.

이번 결론

검색은 단계적으로 올리고, 답변보다 근거를 먼저 설계합니다.

개인 학습 사이트와 코딩 작업에서는 대부분 rg, 문서 링크, Git history, 공식 문서 확인으로 시작합니다. 문서가 많아지고 같은 지식을 반복해서 찾게 될 때 file search나 vector store를 붙이고, 여러 agent가 검색 결과를 나눠 쓰기 시작할 때 agentic RAG로 봅니다.

용어를 분리하기

용어 이 사이트에서의 뜻 먼저 확인할 것
Search 키워드, 파일명, symbol, Git history로 찾는 기본 검색 repo 구조, AGENTS.md, README, 테스트 이름
Retrieval 질문에 필요한 자료 조각을 찾아 agent에게 넣는 과정 출처, 최신성, 권한, 중복 자료
Vector store 문서를 semantic search 가능한 색인으로 저장하는 계층 chunking, metadata, 갱신 주기, 삭제 정책
RAG 검색 결과를 근거로 모델 응답을 만들고 출처를 남기는 패턴 검색 품질, citation, 환각 방지, fallback
Agentic RAG agent가 검색 계획, 도구 선택, 재검색, 검증을 루프 안에서 수행하는 구조 권한, 비용, latency, eval, 관찰 가능성

도입 단계

  1. Local search: rg, 파일 트리, Git diff, README, AGENTS.md로 충분한지 먼저 확인합니다.
  2. Curated reference: 공식 문서 링크와 학습 HTML을 reference index에 모아 사람이 읽을 수 있게 둡니다.
  3. File search: 문서 묶음이 커지고 키워드 검색으로 놓치는 내용이 많아지면 파일 기반 검색을 붙입니다.
  4. Vector store: 의미 기반 검색, chunk metadata, 문서 freshness 관리가 필요할 때 색인을 둡니다.
  5. Agentic RAG: 검색, 검증, 재시도, 요약, 인용을 agent가 작업 루프 안에서 선택해야 할 때 도입합니다.

Memory는 RAG가 아니다

agent에게 오래 남겨야 할 정보가 모두 vector store로 가는 것은 아닙니다. 먼저 가장 작은 기억 계층을 고르고, 반복 검색 문제가 실제로 생길 때 retrieval 계층을 올립니다.

계층 적합한 내용 예시
AGENTS.md 작업 규칙, 검증 규칙, 프로젝트 경계 커밋 정책, 테스트 명령, 인코딩 주의
Design docs 재사용될 제품/기술 결정 아키텍처 결정, 운영 원칙, 공개/비공개 분리
Skills 반복 절차와 참고 자료 문서 갱신 루틴, 배포 검증 루틴
Session summary 현재 작업 맥락 이번 턴에서 한 변경과 남은 작업
Vector memory 많은 문서에서 의미 기반으로 다시 찾아야 하는 지식 학습 노트 묶음, FAQ, 운영 사례
Structured DB 정확한 상태와 관계가 중요한 데이터 프로젝트 registry, 배포 상태, 권한, 이벤트 로그

무엇을 저장할까

자료 추천 저장 방식 주의
공개 학습 HTML site index + file search 후보 사람이 읽는 문서가 먼저이고 검색 색인은 보조입니다.
공식 문서 링크 reference page + 갱신 날짜 전문 복사보다 URL, 확인일, 핵심 판단만 남깁니다.
개인 playbook 비공개 repo 또는 user-local notes 로컬 경로, 계정, 토큰, 실험 로그는 공개 HTML에 넣지 않습니다.
프로젝트 운영 규칙 AGENTS.md, README, design docs agent가 실제 작업할 때 자동으로 읽는 위치를 우선합니다.
대화/작업 이력 요약 문서, changelog, issue 원문 전체보다 결정과 근거를 구조화합니다.
테스트 실패와 복구 기록 reference 또는 private postmortem 반복 실패 패턴만 검색 대상에 넣습니다.

Agent workflow에 넣기

Plan 검색 계획

질문을 먼저 쪼갭니다. 코드 구조, 공식 문서, 운영 기록, 사용자 결정 중 어디를 찾아야 하는지 분리합니다.

Retrieve 근거 수집

검색 결과를 그대로 믿지 않고 파일 위치, 문서 URL, 날짜, version 조건을 함께 가져옵니다.

Synthesize 작업 판단

agent는 찾은 자료를 바탕으로 선택지를 줄입니다. 모호하면 재검색하거나 사용자 결정이 필요한 지점을 표시합니다.

Verify 검증 루프

답변이나 구현 뒤에는 테스트, 링크 확인, 브라우저 증거, citation 점검으로 검색 품질을 되돌아봅니다.

코딩 작업에서의 판단표

상황 추천 이유
단일 repo의 함수나 컴포넌트를 수정 rg + targeted read 현재 코드가 source of truth라서 색인보다 직접 읽는 편이 정확합니다.
여러 프로젝트의 운영 규칙을 비교 문서 index + structured table 반복 참조할 기준을 사람이 읽을 수 있게 정리하는 것이 먼저입니다.
공식 API가 자주 바뀜 공식 문서 실시간 확인 오래된 vector 색인은 오히려 위험합니다.
내 학습 문서가 많아져 찾기 어려움 file search 또는 local vector index 내가 쓴 설명을 의미 기반으로 다시 찾을 필요가 생깁니다.
agent가 문서 검색 후 구현까지 반복 agentic RAG + eval 검색 품질이 구현 품질로 이어지므로 평가 루프가 필요합니다.
권한이 섞인 private/public 문서 분리 저장 + metadata 권한 검색 편의보다 유출 방지가 우선입니다.

Vector store 설계 메모

  • Chunking: 문서 구조를 잃지 않도록 제목, 섹션, 코드 블록 단위의 경계를 보존합니다.
  • Metadata: source URL, repo, path, updated date, audience, public/private 여부를 넣습니다.
  • Freshness: 공식 문서는 색인만 믿지 말고 최신 여부를 다시 확인하는 루틴을 둡니다.
  • Permissions: 공개 사이트, 개인 playbook, 고객 프로젝트, 비밀 값은 같은 색인에 섞지 않습니다.
  • Citations: agent 답변이 “어디서 왔는지”를 남기게 해야 나중에 고칠 수 있습니다.
  • Deletion: 잘못된 문서와 오래된 결정을 색인에서 제거하는 절차가 있어야 합니다.

Graph와 Hybrid는 언제 보나

GraphRAG나 HybridRAG가 항상 더 좋은 것은 아닙니다. 일반적인 문서 검색은 keyword search, semantic search, metadata filtering 조합으로 충분한 경우가 많고, 관계 자체가 답의 핵심일 때만 graph 계층을 검토합니다.

방식 쓸 때 비용
Keyword/BM25 정확한 파일명, API 이름, 오류 메시지를 찾을 때 빠르고 예측 가능하지만 표현이 다르면 놓칠 수 있습니다.
Vector search 같은 뜻의 다른 표현, 긴 문서 묶음, 학습 노트를 찾을 때 chunk 품질과 freshness 관리가 필요합니다.
Hybrid search 정확한 키워드와 의미 검색을 함께 써야 할 때 튜닝과 평가가 없으면 복잡도만 늘 수 있습니다.
GraphRAG 엔티티 관계, 의존성, 규칙 연결망이 답의 핵심일 때 스키마, 추출 품질, 업데이트 비용이 큽니다.

Eval을 같이 둬야 하는 이유

RAG 품질은 “그럴듯한 답변”으로 평가하면 금방 무너집니다. 검색 결과가 맞는지, 오래된 자료를 골라오지 않았는지, private 자료를 공개 답변에 섞지 않았는지 확인하는 작은 eval이 필요합니다.

  1. 대표 질문 10개를 만든다.
  2. 기대 출처와 금지 출처를 함께 적는다.
  3. 검색 결과에 citation이 있는지 확인한다.
  4. 답변이 최신 공식 문서와 충돌하면 실패로 본다.
  5. 실패한 질문은 chunking, metadata, prompt, tool 선택 중 무엇이 문제인지 분류한다.

실패 모드

  • Stale retrieval: 오래된 공식 문서나 예전 모델 기준을 최신 답처럼 사용합니다.
  • Bad chunking: 제목, 조건, 코드 블록이 분리되어 근거가 반쪽만 검색됩니다.
  • Private leakage: 개인 playbook이나 고객 프로젝트 문서가 공개 답변에 섞입니다.
  • Permission blur: agent가 읽어도 되는 자료와 쓰면 안 되는 자료의 경계가 흐려집니다.
  • Citation drift: 답변은 맞아 보이지만 링크나 파일 위치가 실제 근거와 어긋납니다.
  • Retrieval loop: 충분한 근거가 있는데도 agent가 검색만 반복하고 결정을 미룹니다.
  • Over-indexing: 작은 프로젝트에 큰 검색 인프라를 붙여 유지보수 비용이 더 커집니다.

이 사이트의 다음 적용

  • Agentic stack 문서는 전체 구조를 설명하고, 이 문서는 RAG와 검색 계층을 세부화합니다.
  • Custom agents 문서의 docs-maintainer 역할에 공식 문서 확인과 public/private 분리를 연결합니다.
  • content audit에는 어떤 문서가 검색 후보인지, legacy인지 계속 표시합니다.
  • 다음 문서 후보는 codex/update-routine.html 또는 legacy 원본 MD 매핑입니다.
